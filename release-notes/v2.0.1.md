# v2.0.1 — Room Area Labels + Three Bug Fixes

Everything since v2.0.0: one new feature and three bug fixes, found via a
screenshot review of the card running against a live Roomba 980.

---

## New: room area annotation on Map tab labels

`region_areas_m2` (integration v2.9.1) lives on the CloudSmartZoneSelect
entity (`select.*_smart_zone_select` / `_zone_select` fallback), the same
location as the existing `region_icons` attribute — **not** on the image
entity that supplies the `rooms` dict used for room geometry. This is a
deliberate cross-entity join, by room name, done entirely in the card: the
Map tab's room boundary labels now look up `region_areas_m2[room.name]` from
the select entity and append the area when present, e.g. "Kitchen / 20.0 m²".

Per the integration's own architecture (labels are drawn by the card only
since v2.7.3, to avoid duplicate labels once the card started drawing its
own), this follows the same card-side-only convention — no integration
change requested or required.

**Graceful degradation:** area present for that room → appended; area
attribute exists but lacks that specific room (partial cloud data) → name
only; select entity entirely absent (local-only setup, integration < 2.9.1,
inactive floor, or an EPHEMERAL robot with no CloudSmartZoneSelect entity at
all) → name only; malformed attribute → name only. Never an error.

## Bug fix: Map tab showed a redundant, confusing internal toggle

The Map tab and the standalone History tab both reuse the same zone-rendering
function with a forced sub-state (`'coverage'` for Map, `'calendar'` for
History) rather than each having fully separate code. The internal
Calendar/Coverage pill toggle that belongs to that shared function rendered
regardless of which top-level tab was using it — so tapping "Calendar" while
on the Map tab silently swapped its content to the calendar heatmap, with
the top-level tab bar still showing "Map" as active and no way back except
switching tabs away and back.

Fixed with a `suppressSubTabToggle` flag: suppressed on the Map tab and the
standalone History tab (each already corresponds to exactly one of these
views at the top level), shown only in companion mode's History tab — the
one case where no separate Map tab exists to hold the coverage view.

## Bug fix: missions with `stuck_and_resumed` showed the failure icon

A day's calendar cell colour and "X% completion rate" line are driven by
`DaySummary.completed`, which the integration defines as missions with
result `completed` **or** `stuck_and_resumed` ("Robot stuck but continued
and finished" — a real success, not a failure). The day-detail popover's
per-mission icon, however, only matched the literal string `'completed'` —
every other result value, including `stuck_and_resumed`, got the ✗ failure
icon. A day could show a fully green cell and "100% completion rate" while
every individual mission inside it displayed ✗, which is exactly the
contradiction a screenshot turned up.

Fixed by grouping the same two result values the integration already groups
for `DaySummary.completed`, instead of a literal-equality check against
`'completed'` alone. Genuine failures (`error`, `cancelled`,
`stuck_and_abandoned`, etc.) are unaffected and still show ✗.

## Bug fix: WiFi sparkline's "X% min" label was reading raw counts as percentages

Traced directly to the integration source rather than guessed at:
`sensor.py` confirms `wlBars` — the field `wifi_signal` is sourced from — is
a 5-element histogram where **the value at each index is a count of readings
in that signal-strength bucket**, not a percentage ("index = signal bucket,
value = count"). The card's `normalisedWifiPct()` treated a 5-element array
as "already bucket percentages, pass through unchanged" — a count like
`[0, 1, 1, 0, 3]` was displayed as if it meant "0%, 1%, 1%, 0%, 3%", which is
meaningless. Because most missions have at least one empty bucket, the
reported "minimum" was very nearly always 0% regardless of actual signal
quality — which is what a screenshot showing "0% min" on a mission with a
seemingly fine connection turned out to be.

This also means the data is a static end-of-mission distribution, not a
time-ordered sequence — there's no real "minimum reading during the
mission" to report from a histogram shape. Fixed by computing the
weighted-mean signal quality % using the exact same formula the
integration's own `wifi_health` sensor uses per mission
(`_raw_wifi_quality_pct` in `sensor.py`): weighted mean bucket index, scaled
from 0.0–4.0 to 0–100%, displayed as "{quality}% avg" instead of "{min}% min".

The older variable-length time-series shape some integration versions may
still send (per `REST_API_CONTRACT.md`'s own 6-element example payload) is
unaffected — that branch's original "minimum reading" semantics are
unchanged, since that genuinely is a time-ordered sequence.

A pre-existing test for the 5-element case happened to keep passing through
this entire bug because its fixture's counts summed to exactly 100 — a
coincidence under which "pass through unchanged" and "normalise to % of
total" produce numerically identical output, masking rather than catching
the bug. Replaced with a fixture that doesn't share that coincidence, plus
6 new tests for the corrected weighted-mean calculation.

## Not a card bug — flagged for the integration instead

A screenshot showed a day-detail popover header reading "3 missions" while
only 2 mission rows rendered underneath. Live data confirmed the card is
displaying both source values correctly as received: `format=summary`
reports `DaySummary.total = 3` for that date, while `format=records` returns
only 2 records with that date in the same 28-day window. The two integration
endpoints disagree about how many missions occurred that day — written up
separately for the integration workstream, no card-side action needed.
