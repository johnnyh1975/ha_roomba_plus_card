# Roomba+ Card v2.3.0 — Integration-Enablement Wave

> **Minimum integration:** 2.8.6 (unchanged). The full v2.3.0 feature set needs
> integration ≥ **3.3.0**; every new feature is presence-gated and degrades
> gracefully on older versions. **Breaking changes:** none.

This release closes out the v2.3.0 outlook: every item that was blocked
waiting on an integration surface (F22, ZONE-OVERLAY, F24, F23, and the
long-standing Explain-for-cloud-rows gap) shipped on the integration side
during this cycle, and the card now consumes all of them. Alongside that,
three new integration-v3.3.0 surfaces (MISSION-MAP, ROOM-SCHED, CROSS-CORR)
get their own card-side features for the first time. It also fixes a
standing bug that likely meant the Map tab's room-overlay feature never
rendered for anyone, on any integration version, since v2.0.0.

## Fixed

### Room overlays were reading the wrong entity — since v2.0.0

`hasAlignment` and the C7-ROOM-BOUNDS room-polygon overlay (Map tab) read
`rooms`/`calibration_points` from `image.*_coverage_map`. Verified against
integration source: that entity (`RoombaCoverageImage`) is an unrelated
GridStore EMA-diagnostic heatmap that has never carried either attribute.
The entity that actually carries them is `image.*_map` (`RoombaMapImage`).
`hasAlignment` therefore likely evaluated `false` for every installation —
the room-overlay feature may never have rendered, on any integration
version, since it was built.

Fixed by reading `rooms`/`calibration_points`/`zones`/`door_markers`/
`furniture_candidates` from the correct entity, positioned via a new
client-side transform derived from `calibration_points` (3 pose-mm↔px
anchor pairs — the same mechanism xiaomi-vacuum-map-card already uses,
replicated here) rather than the coverage entity's unrelated bounding box.
The Map tab's displayed picture and hazard-pin positioning are
deliberately left untouched — both already work correctly off
`image.*_coverage_map`'s own bbox, and touching them wasn't necessary to
fix the actual bug.

**Open verification point:** whether the two images (`image.*_map` and
`image.*_coverage_map`) share compatible framing/scale hasn't been
field-confirmed. If they don't, the new overlay will render visibly
offset from the picture beneath it — obviously wrong, not subtly wrong,
so it should surface immediately in field testing rather than silently
mislead.

### Why? now works on cloud-source mission rows

The explain endpoint previously 404'd for any cloud-only row (their
synthetic `c_{ts}` ids were never resolvable against
`MissionStore.find_by_id()`) — the card worked around this by hiding the
button entirely for `source !== 'local'` rows (R2-1, v2.2.0). Integration
3.3.0 added a dedicated cloud-id resolution path; the card's
`source === 'local'` gate is removed accordingly. The Map button
(MISSION-MAP replay) keeps its equivalent gate — verified that its
record-resolution path is a separate lookup that didn't get the same fix.

## New

### Mission coverage replay — "Map" button *(integration ≥ 3.3.0 MISSION-MAP)*

A third action next to Why?/Route in the History tab's day-detail row.
Renders the mission's actual coverage — room outlines behind, coverage
points on top — client-side from the integration's `map.json` endpoint.
Self-contained: computes its own bounding box from the payload rather
than reusing the live map's transform, since the two coordinate spaces
are verified to differ (UMF-space vs. pose-space). Gated the same way as
Why? before this release (`source === 'local'`) plus `n_mssn != null` —
a 404 (no coverage layer, e.g. still-unconfirmed i-series firmware)
renders as a calm, honest answer, not an error.

### Rooms-overdue widget *(integration ≥ 3.3.0 ROOM-SCHED, SMART + cloud)*

A new "ROOMS" block in the Health tab shows which rooms are due for
cleaning and how overdue each one is, sourced from
`sensor.*_rooms_overdue`. Zero overdue renders as a real, calm answer
("All rooms in rhythm") rather than being hidden. A "Clean overdue"
button — visible only when something actually is overdue — triggers
`roomba_plus.clean_overdue_rooms` via the card's existing generic
service-call mechanism. The Health tab badge now also fires when the
overdue count is greater than zero.

### Zone, door, and furniture overlays *(integration ≥ 3.3.0 ZONE-OVERLAY / F24)*

The Map tab's room overlay gains three siblings, gated on their own
capability flags and the same aligned-mode requirement as rooms: observed
obstacle markers and keep-out zone outlines, door markers (with a
mission-count tooltip), and furniture-shadow markers where the integration
has flagged a likely layout change.

### Hazard-pin time patterns *(integration ≥ 3.3.0 F22)*

Stuck-hotspot pins on the Map tab now show a dominant day/time pattern in
their tooltip when the integration has found one ("usually Mon ~9am").
Pins below the pattern-detection confidence threshold get a shared
footnote explaining the gap rather than looking silently broken.

### Dirt/sensor correlation widget *(integration ≥ 3.3.0 CROSS-CORR, opt-in)*

A new Health tab block for the opt-in dirt-correlation feature: shows the
strongest passing correlation with its friendly entity name and r value,
or per-entity sample-count progress toward the 30-sample threshold while
still collecting data. The card shows the numbers as-is rather than
inventing interpretive language the raw correlation coefficient alone
doesn't fully justify — that framing is left to the integration's own
Repair Issue.

## Under the hood

- **Test-typecheck hardening.** `tsconfig.json` now typechecks `tests/`
  as well as `src/` (previously excluded entirely — a tracked gap since
  v2.2.0). Surfaced and fixed 98 pre-existing errors: mostly test
  fixtures that fell out of sync with their interfaces across several
  past releases, plus two genuine bugs (`makeHass()` called with a raw
  string instead of a proper fixture in two `capabilities.test.ts`
  cases — passed only because a truthy string satisfies the same
  presence check a real fixture would; a wrong relative import path in
  `heatmap.test.ts`).
- New module `calibration.ts` — derives an mm→px transform from 3
  `calibration_points` anchor pairs, independent of any bounding box.

### Two review rounds (per convention) — findings

- **Unavailable/unknown sensor false-positives.** The new Rooms-Overdue
  and Dirt-Correlation widgets checked only for entity *presence*, not
  *state* — an unavailable `sensor.*_rooms_overdue` would have rendered
  the calm "All rooms in rhythm" message instead of an honest absence.
  Fixed with the same unavailable/unknown guard already used elsewhere
  in this file. Caught mid-fix that this doesn't generalise: the
  dirt-correlation sensor's `state: 'unknown'` is the *normal* case
  whenever nothing has passed the correlation threshold yet — treating
  it as "hide" would have broken the sample-count progress display it
  exists to show. Only `'unavailable'` hides that one; `'unknown'` does not.
- **Reset-popover cross-talk.** The generic `data-reset` handler
  unconditionally closed *any* open popover on success — harmless for
  the existing retention/filter/brush resets (whose reset button lives
  inside the very popover it closes), but the new inline "Clean overdue"
  button doesn't live in a popover at all. Tapping it could have silently
  closed an unrelated popover open elsewhere on the Health tab. Fixed:
  the handler now only clears `openPopover` when it matches the reset's
  own key.
- **Silent NaN propagation in `calibration.ts`.** `buildCalibrationTransform()`
  checked that the three anchor points existed but not that their
  coordinates were actual finite numbers — malformed integration data
  would have silently produced NaN pixel positions (a garbled overlay)
  instead of cleanly rendering none. Added an explicit finite-number
  validation pass.
- **README bug, found while updating it for this release:** the
  companion-mode xiaomi-vacuum-map-card examples told users to set
  `map_camera: image.<robot>_coverage_map` — the same wrong entity the
  card itself was reading before this release's fix. Anyone who followed
  those examples would have configured XVMC to read `rooms`/
  `calibration_points` from an entity that has never carried either.
  Corrected to `image.<robot>_map` in all three examples.
