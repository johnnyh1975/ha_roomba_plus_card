# Roomba+ Card v2.2.0 — Honest Signals

> **Minimum integration:** 2.8.6 (unchanged). The full v2.2 feature set needs integration ≥ **3.2.1**; every new feature is presence-gated and degrades gracefully on older versions.
> **Home Assistant:** ≥ 2024.1 (unchanged). **Breaking changes:** none.

The theme of this release: every signal on the card should tell you what is true *right now*, judged against *your* robot — an active error vs. one you fixed last week, a hard failure vs. a mission that merely ended with a warning, a plain-language reason instead of a bare ⚠.

## Fixed

### The error banner no longer outlives the error

The Health tab's error banner was driven by `sensor.*_last_error_code` — which is *deliberately* persistent ("last error", paired with a timestamp). The result: a brush-jam banner that stayed red for a week after the jam was physically cleared. The banner is now gated on the vacuum entity's **active** error (the `error_code` attribute the integration only sets while an error is live), with a fallback to the vacuum's own error attributes so an active error is never silent. A resolved error now renders as a muted informational line instead: *"Last error: Brush stuck · 6 days ago (resolved)"* — the history stays visible, without the alarm styling.

### Calendar cell colours now match the mission icons

v2.0.2 introduced the three-tier mission classification (✓ success / ⚠ caution / ✗ failure), but the calendar heatmap kept its old colour table — and relative to the tiers, the two were **inverted**: a day whose worst mission was `stuck` (a hard failure needing physical intervention) rendered amber, while a day whose worst mission was `error` (caution tier — the mission ended) rendered red. Field report: a day containing only two ⚠-tier missions showed a red cell. Now: `stuck` → red, `error` → amber. `cancelled` deliberately stays neutral grey — a day whose *only* missions were user-cancelled is not a warning condition.

Two related integration-side issues found during this work were fixed in integration 3.2.1 (day-dominance now ranks `stuck` above `error`, and `error_*` variants no longer fall through to an uncoloured day). The card's colour mapping is version-agnostic and renders both 3.2.0 and 3.2.1 responses correctly.

## New

### "Why?" — plain-language anomaly explanations *(integration ≥ 3.2.0)*

Missions that didn't end cleanly get a **Why?** button in the day detail. One tap asks the integration to judge that mission against this robot's own history and returns a plain-language reason — *Obstacle or blockage · Excessive recharging · Unusually dirty area · Incomplete coverage* — plus a recommended action, and a note when the robot was picked up mid-mission. "Nothing statistically unusual" is a real answer too: it means the result code above is the whole story. Local-history missions only (see Known limitations in the README).

### "Route" — mission path replay *(integration ≥ 3.2.1)*

A **Route** button on missions replays where the robot went, room by room: *09:05 Kitchen → 09:23 Hallway → 09:31 Bedroom*. Room-granular by design — reconstructed from the mission archive, not pixel pose tracking. Requires the per-mission counter integration 3.2.1 adds to history records; on local-source rows it arrives via cloud backfill, so the button can appear shortly after the mission itself does.

### Health score trend + calibration countdown *(integration ≥ 3.2.0)*

A trend arrow next to the robot health score — ↗ improving / → stable / ↘ declining — judged against this robot's own learned baseline, not a fixed threshold. While the 44-day baseline is still building, the card shows the countdown the integration exposes for exactly this purpose ("trend in ~31d") instead of a silent blank.

### Plain-language health status *(integration ≥ 3.1.0)*

Below the score, the integration's own `status_text` and `recommendation` now appear — e.g. *"Battery capacity is declining — keep an eye on the retention sensor."* Localised server-side in all seven integration languages; the card displays, it doesn't interpret.

### Layout-change alert *(integration ≥ 3.2.0)*

When the integration's layout-change detection fires (coverage pattern diverging from the robot's learned layout — moved furniture, new or removed obstacle), the Health tab shows an alert and its badge dot. Lowest alert priority: informative, not urgent.

### Dock health block *(Clean Base robots)*

The Health tab's details section gains a DOCK block: tank level (enabled by default where reported) and lifetime knockoff / charge-abort / contact-chatter counters (disabled-by-default diagnostics — enable the entities and the card picks them up). Renders whatever subset exists; renders nothing on robots without a dock that reports these (e.g. the 980).

### Lifetime dirt-detection counters

The History stats footer gains a dirt-detect line (optical / piezo / scrub-event lifetime counters) when those diagnostic sensors are enabled. Lifetime counters live in the lifetime footer — deliberately not in the per-mission day detail.

### Recharge-aware duration in the header

During a mission that included a mid-mission recharge, the header's status line now shows the honest pair: *"156 min (42 min charging)"*. A long wall-clock duration reads very differently once you can see how much of it was charging rather than struggling. Only shown when there actually was recharge time; either number alone would mislead, so they only appear together.

## Under the hood

- Two full review rounds after feature completion caught and fixed, pre-release: a Why?-button 404 on cloud-sourced history rows (their API-layer ids aren't resolvable by the integration's mission store — verified against 3.2.0 *and* 3.2.1 source), a forever-loading state when the API client wasn't ready at tap time, the dock block ignoring the health-details collapse, a degenerate "Error: Error" label, and a drift between the render-guard test replica and production (`_phase` vs `_mission_phase`).
- All new attribute reads are explicit-`null` safe; all new data paths are HTML-escaped, including attribute contexts.
- Ten new entities added to the render guard; test replica synced with per-id assertions.
