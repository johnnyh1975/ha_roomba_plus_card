# v2.1.0

Feature release adding header indicators, Favourites, and prompter history refresh, plus an architecture and code-review hardening pass over the v2.0.4 codebase. No breaking changes, no config migration needed.

**Requires:** roomba_plus integration ≥ 2.8.6 (Favourites entity-id stabilisation benefits from integration ≥ 3.0.0 — see below)

---

## New features

### Connectivity indicator in the header

When the robot's cloud link drops or its local MQTT link goes silent mid-mission, a small "☁ Robot offline" / "☁ Cloud offline" badge now appears next to the robot name in the header. It's invisible in the normal connected state — no chrome for the happy path. Reads `binary_sensor.*_cloud_connected` and `binary_sensor.*_mqtt_stale`.

### Firmware badge

After a firmware change, an "⬆ FW <version>" badge appears next to the robot name for 24 hours, then disappears on its own. Reads `sensor.*_firmware_version`.

### Current-room line during a mission

While a mission is active, the header can show the room the robot is currently in (📍 Kitchen), sourced from the `device_tracker.*_position` entity. On SMART robots this is suppressed when the existing spatial line already shows the same room, so there's no duplicate. EPHEMERAL robots don't report a room estimate, so the line is simply absent there.

### Favourites in the ⚙ tab

If you've defined favourite cleaning routines in the iRobot app, they now appear as one-tap buttons in the ⚙ tab. Each button fires its routine via `button.press`. No configuration needed — the card discovers favourite buttons automatically.

> **Best with integration ≥ 3.0.0.** Favourite button entity-ids are now stable and locale-independent (`button.<robot>_fav_<id>`) thanks to the integration's v3.0.0 `suggested_object_id` fix and the v22→v23 migration that renames existing favourites. On older integrations the entity-ids derive from the (locale-dependent, user-chosen) routine name and the card may not discover them.

### History refreshes immediately at mission end

The History tab previously reloaded when it happened to observe the `mission_active` sensor flip from on to off. The card now also subscribes to the integration's `roomba_plus_mission_completed` event, so history updates promptly even if the card wasn't actively rendering at the exact moment the mission ended. In multi-robot setups the event is filtered by config entry, so one robot finishing never reloads another's history. The old state-transition trigger remains as a fallback for environments without a WebSocket connection.

### Mission anomaly banner (integration ≥ 3.0.0)

When the robot logs three or more consecutive anomalous missions, the Health tab shows a banner prompting a brush/filter check. Reads `sensor.*_consecutive_mission_anomalies`. This sensor is **disabled by default** in the integration — enable it in Home Assistant for the banner to appear. The threshold is three (two consecutive anomalies can be coincidence; three are a pattern).

### Navigation health panel (integration ≥ 3.0.0)

The Health tab can show a collapsible navigation panel: the navigation quality score (0–100, colour-coded) plus the contributing factors — panic events, landmark quality, and good-landmark count — so you can see *why* navigation quality is low, not just that it is. Reads `sensor.*_nav_quality` / `_nav_panics` / `_nav_landmark_quality` / `_nav_good_landmarks`. These are **disabled by default** in the integration; enable them to use the panel. The factors are shown as honest raw values rather than graded indicators, since reliable good/bad thresholds for them aren't established.

## Bug fixes

**Multi-robot: actions could target the wrong robot**

All header and control actions — start, pause, resume, return home, locate, stop, retry, repeat mission, pass-count, room targeting, and the "Mark as replaced" maintenance resets — were sent to the configured default robot (`config.entity`) rather than the robot currently being viewed. In a multi-robot card, tapping "Start" while looking at the second robot would have started the first. The header's live state read had the same issue. All now target the active robot. Single-robot setups are unaffected.

## Under the hood

These changes have no user-facing behaviour but improve maintainability and robustness.

**Event handling rewritten as delegation** — The card previously re-attached ~22 groups of DOM event listeners on every single render (each render rebuilds the card's inner HTML). This is now three delegated listeners registered once on the card's shadow root, which survive the re-render. This removes a class of subtle issues where focus, scroll position, and CSS transitions could break on state updates, and eliminates listener re-wiring as a per-render cost. The dispatch table is unit-tested.

**Config editor matches the v2.0 tab model** — The visual config editor (`getConfigForm`) still presented the old v1.x "show … zone" switches as if they were layout controls. It now leads with the real v2.0 switches (`mode`, `default_tab`) and groups the legacy content-visibility toggles under an "Advanced" section. The deprecated `show_settings` alias is no longer offered to new users (it still works in YAML for back-compat).

**Dead code removed** — `status-zone.ts` (superseded by the persistent header since v2.0) and its tests were removed.

**Smaller hardening** — Defensive JSON parsing in the carpet-boost cycle handler; a single source of truth for timer cleanup; corrected a misleading code comment about `alignment_confidence` (the field is real — populated for cloud-source records by the integration's UMF aligner — only the comment was wrong); and a stray type cast removed so the project now type-checks with zero errors.

---

## Upgrade notes

No config changes needed. All `show_*` options continue to work, now grouped under "Advanced" in the visual editor.

For the best Favourites experience, upgrade the `roomba_plus` integration to 3.0.0 or later — it stabilises favourite entity-ids so the card discovers them reliably, and migrates any existing favourite entities automatically on upgrade.
