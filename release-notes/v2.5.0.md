# Roomba+ Card v2.5.0

> **Minimum:** integration **4.2** (was 2.8.6) · Home Assistant **2025.5**
> (was 2024.1), the same minimum as the integration itself. **Recommended:
> integration 4.2.19 / 4.3.0b7**, which fix the integration-side gaps this
> release found (see the end of these notes). Verified against 4.2.18,
> 4.2.19, 4.3.0b6 and 4.3.0b7. **Breaking change:** status values are now read as the slugs the
> integration has sent since 4.1.8; on older integrations some status texts
> read wrong (e.g. "Robot not ready: Ready"). Update the integration first —
> the card now says so itself (see below).

The integration has moved from 3.5 to 4.2/4.3 since the card was last
aligned with it. It switched its status values to translatable slugs,
renamed or regrouped a number of entities, and gained a second robot
generation (Prime / V4). None of that broke the card loudly — it quietly
lost features instead: the room picker vanished on every cloud install, a
ready robot read "not ready" (#17), the coverage bar and pad bar never
appeared, and the map overflowed desktop screens (#20). This release puts
the card back in step with the integration, and ships the July work (Gentle
Mode, fleet health, household skeleton, 8 languages) alongside it.

## New minimum versions, checked by the card

| | before | now |
|---|---|---|
| Home Assistant | 2024.1 | **2025.5** (same as the integration) |
| `roomba_plus` integration | 2.8.6 | **4.2** |

HACS enforces the Home Assistant minimum (`hacs.json`). For the integration
nothing did, so the card checks both itself when it loads: Home Assistant
from its own config, the integration through Home Assistant's `manifest/get`
(also allowed for non-admin users). If either is older, a short notice at
the top of the card names the needed and the installed version, in your
language. Unknown or unreadable versions produce no notice. Beta versions
count as before their release (4.2.0b3 < 4.2.0; 4.3.0b6 is fine).

## Back in step with integration 4.x

### Readiness: a ready robot no longer reads "not ready" (#17)

`sensor.*_readiness` reports `ready`, `bin_full`, `lid_open`, … since
integration 4.1.8. The card compared against `'Ready'`, so every ready robot
with maintenance due showed **"Robot not ready — check the app"**. It now
compares against slugs and, when the robot really is not ready, says why in
the integration's own words — "Robot not ready: Lid open", in your language.
Thanks to **@azrael-229** for the precise analysis, including the point that
the test fixture `st('Ready')` had cemented the bug: fixtures now use the
real slugs, with a negative control.

### Header states from the phase sensor

- **Emptying bin** (`emptying_bin`) finally shows. The header compared
  against the raw MQTT value `evac`, which the phase sensor never reported —
  this state had never appeared. No action buttons during the 10–20 s the
  dock is busy.
- **Recharging mid-mission** (`charging_mid_mission`) is taken from the
  integration directly, no longer inferred from `mission_active` and an ETA.
- **No contact with robot** (`no_contact`, `not_responding`) replaces a
  stale "Docked" when the integration has not heard from the robot.
- **Pad washing / drying, tank refilling** show the integration's text.

### Room selection is back on cloud installs

With iRobot cloud credentials (the normal setup) the integration replaces
`select.*_smart_zone_select` with one `select.*_cloud_zone_<map>` per map.
The card only knew the former, so the **Rooms…** button, the room picker,
room icons and room areas never appeared. The card now uses the active
map's select (never an inactive floor's), and room icons appear for the
first time: the integration sends full `mdi:` icon names, which the card's
icon table never matched; all 22 iRobot room types now have an emoji.

### Current room while cleaning

The device tracker is `device_tracker.<robot>` — the card looked for
`device_tracker.<robot>_position`, so the "📍 Kitchen" line never showed.
It now reads the tracker's structured `room` attribute instead of filtering
display labels out of its state; a localized status ("Bloqué", "Dock busy")
can no longer be mistaken for a room name.

### Health tab

- **Coverage bar** returns — `coverage_pct` on `cleaning_performance`
  (the old `recent_coverage_pct` sensor was removed in integration 3.0). It
  compares the last run with your usual area, so it can read above 100 %;
  the bar is capped, the number is not.
- **Pad** shows days remaining ("~9 days left", red at ≤ 3) from
  `pad_days_until_due`. The bar waited for an attribute the integration
  never had and had never rendered.
- **Filter / brush** bars measure against `max_hours` — iRobot's own full
  life, matching the cloud counter the remaining hours come from — instead
  of the local threshold, which could pin the bar at 100 %. The wear alerts
  use the same reference. A display unit changed in HA (days, minutes) is
  converted back.
- **Clean Base, mop pad, mop intensity, carpet boost** show the
  integration's text instead of raw values like `reusable_wet`. Clean Base
  problems (bag full, clogged, …) are highlighted. The old mapping had
  `empty` (bin just emptied) as "Bag full".
- **Carpet boost** no longer appears as a dead control where integration
  4.2.15 retired it (robots without `cap.carpetBoost`).

### Map tab fits the screen, overlays line up (#20)

The coverage picture is square; on a wide desktop column it scaled past the
bottom of the screen. The card now shows only the part of the picture the
grid covers — on a wide, short home most of the square was transparent —
capped at 70 % of the viewport height, with every overlay positioned in the
same box. Thanks to
**@azrael-229** for the report.

Overlays now use the picture's own pixel frame, reproduced exactly from the
integration's renderer (one shared scale, half-cell offset). Before, pins
were stretched per axis — off on every non-square floor plan — and room
outlines, keep-out zones, doors and furniture were placed with the
calibration of a *different* picture (`image.*_map`), which is why they
never lined up. Obstacle and keep-out **pins** had the same problem from the
other side: the integration sent them in map units rather than robot
coordinates, so they always landed in the wrong place. Integration 4.2.19
converts them and labels every pin with its frame (`space`); the card places
only pins in robot coordinates, and leaves the obstacle and keep-out pins out
where the zone overlay already draws the same obstacles and keep-outs. On
older integrations only the stuck-hotspot pins appear. Room labels for rooms
the robot has never visited are no longer drawn outside the picture.

### Smaller corrections

- **Areas in m² on metric installs.** Home Assistant reports its metric
  length unit as `km`; the card checked for `m`, so every metric install saw
  ft² unless `area_unit: m2` was set. Area sensors are also read in their own
  unit (m² since integration 4.x) — "already today", "vs usual" and the
  lifetime area were off by a factor of ~10.8.
- **Explain** reads `pick_events` and says "Pick-up or dock-contact events
  were recorded" — the integration retracted "robot lifted" after field data
  showed the counter moves on dock contact.
- **History on Prime-only installs** says "History isn't available for this
  robot yet" instead of "requires Roomba+ v1.8". Integrations up to
  4.2.18 / 4.3.0b6 register the history endpoints only for Classic robots;
  from 4.2.19 / 4.3.0b7 Prime history, household and explain work.
- **Long-lived installs** (entries migrated by the integration's schema 21)
  get their battery bar and map overlays back: `sensor.*_battery_level` and
  `image.*_cleaning_map` are recognised.
- **Prime rooms overdue** (`sensor.*_prime_rooms_overdue`, integration ≥
  4.2.19) feeds the same rooms block and Health badge as on Classic;
  *Clean overdue* works for Prime through the same service.
- **Prime favourites** (`button.*_favorite_<id>`) appear in the favourites
  row. With integration ≥ 4.2.19 the History tab and the household view work
  for Prime too. Everything else for Prime / V4 robots comes with 3.0.0.
- **Room-clean errors** show the integration's reason ("Unknown room(s): …")
  instead of "command unclear".
- The render guard now watches the pad, wear-rate and resolved sensors it
  renders.

## Also in this release (July work)

### Start-selected-rooms button: spinner and error now actually show

The "Start selected rooms" action tracked its own send-in-flight state via
`isSendingClean`, a boolean separate from the generic `loadingAction` system
`header.ts`'s button helper checks — so tapping it never showed the spinner,
and a failed send never surfaced `sendError`, even though both were being
tracked correctly under the hood. `header.ts` now receives `isSendingClean`
and `sendError` directly and treats them as first-class loading/error state
for that one button, on the same terms as every other action.

### Gentle Mode switch *(integration ≥ 3.4.3)*

A fourth switch in the ⚙ Settings panel — `switch.*_gentle_mode` — alongside
Edge clean and Always finish, for robots that report it. Same simple on/off
pattern as its neighbours; absent entirely on integrations or robots that
don't expose the entity.

### Household fleet health rollup *(integration ≥ 3.4.3 FLEET-1)*

The Household view's `GET /api/roomba_plus/household` response now carries a
`fleet_health` block — total robot count and which ones need attention — plus
per-robot health trend, battery capacity retention, and maintenance-due
flags. The card surfaces a one-line summary ("All 3 robots healthy" or "1 of
3 need attention: RobotB"), a ⚠ badge per affected robot with a tooltip
naming the specific reason (maintenance due, declining health trend — the
same two conditions the integration's own `needs_attention` computation
uses), and battery retention as a plain informational number alongside each
robot's row. Entirely absent on integrations older than 3.4.3, where
`fleet_health` itself doesn't exist yet.

### Household view loading skeleton

Switching to the Household view previously showed only the "← Back" chip
until the fetch resolved, with a blank gap below it. Two pulsing placeholder
rows now fill that gap, matching the same pulse-animation pattern the Map
tab's heatmap skeleton already used.

### 8-language UI *(card-side, all integration versions)*

The card now reads `hass.language` in every render function and shows UI
text in the matching one of 8 locales — German, English, Spanish, French,
Italian, Dutch, Polish, Portuguese — the same set the integration's own
translations cover. There's no separate card config option for it; it just
follows your Home Assistant language automatically. English is the source
of truth and the automatic fallback for any HA language not in this list,
and for any individual string that's missing from a locale for any reason —
you get English rather than a blank space or a raw key name.

**Translation quality is explicitly two-tier.** English is what was
previously hardcoded, unchanged. **The other 7 (de/es/fr/it/nl/pl/pt) are
first-draft machine translations, not yet reviewed by a native speaker or
field tester** (this note previously claimed a reviewed German — that was
wrong; the README always said 7). Status texts that come from the integration
— readiness, phase, Clean Base, mop pad — are not affected: they now use the
integration's own, maintained translations (see above).
They should be understandable but expect the occasional awkward phrase.
Corrections very welcome as issues or PRs — Thonno, boutXIII, and mdarocha
reviewing Italian, French, and Polish respectively (the locales their own
field-test hardware runs in) would be especially valuable.

Two deliberate, permanent scope limits, documented in the README's new
[Language support](../README.md#language-support) section:

- The visual card editor (⚙ config form) stays English-only — Home
  Assistant calls `getConfigForm()` as a static method with no `hass`
  object available at that point, unlike every other part of this card.
- Pluralization is two-form (singular/plural) only. Languages with more
  grammatical plural forms than that (Polish's few/many split, for
  instance) fall back to the plural form outside the simple singular
  case — always the more-common form, never blank or wrong-language.

## Under the hood

- New `src/entity-ids.ts`: the one place the card still has to guess entity
  ids (cloud zone select, tracker, migrated battery/map ids). 3.0.0 replaces
  it with lookup through HA's entity registry.
- New `src/slugs.ts`: every integration status value the card compares
  against. New `src/relevant-entity-ids.ts`: the render guard's watch list,
  moved out of the card class so tests exercise it; resolved ids are taken
  from both the old and the new `hass`, so an entity appearing counts as a
  change.
- Display of integration states goes through `hass.formatEntityState`
  (HA ≥ 2024.1) with a humanised-slug fallback (`utils.ts formatState`).
- Dev dependency `@types/node` (for the contract test's file access).
- New `src/version-check.ts`: minimum versions, version parsing and the
  notice; the integration version is requested once per page and shared by
  all card instances.
- Re-verified all v2.4.0 assumptions (rooms_overdue, suggested intervals,
  both room-cleaning services, the mission-map cloud-rows resolver, the
  `?rotate=` parameter, and the ROOM-ACCESS sensor) against integration
  v3.5.1 — byte-identical to v3.4.2 in every case that matters to the card.
- v3.5.0's Repairs-panel redesign (dropping the `room_accessibility_low`
  repair issue) doesn't affect the card, which reads the sensor directly,
  not HA's repair registry. v3.5.0 renamed `relocalisation_rate.alert` to
  `.percentile_rank` — the card doesn't consume this attribute either way.
  v3.5.1's GS-SMART-UMF bootstrap fix improves aligned-mode reachability
  for SMART-tier poseless robots (i3+); adjacent to, but doesn't resolve,
  the still-open EPHEMERAL 900-series field-observation item.
- New `src/i18n/` module: a `t(lang, key, vars?)` lookup-and-interpolate
  function, an HA-locale-tag-to-supported-language `resolveLang()`
  (`de-DE` → `de`, unsupported languages → `en`), and one file per locale.
  Every non-English dictionary is typed against English's key set — a
  missing or misspelled key in any of the 7 is a compile-time error, not a
  silent gap discovered later. English dictionary values are byte-identical
  to what was previously hardcoded in each render function, so the entire
  pre-existing (English-default) test suite needed zero changes to keep
  passing.
- Two small separate weekday-abbreviation tables (`WEEKDAY_LABELS`,
  `WEEKDAY_LABELS_SHORT`) cover history.ts's "usually Mon ~9am" pattern
  tooltip and the heatmap's 2-letter calendar column headers respectively.
- `utils.ts`'s `timeSince()` already used `Intl.RelativeTimeFormat` for
  correct, locale-native relative-time strings ("vor 3 Tagen", "il y a 2
  heures") — genuinely more correct than this project's own two-form
  pluralization system, since `Intl` handles each locale's real CLDR plural
  rules. Its fallback path (for environments without
  `Intl.RelativeTimeFormat`, which in practice means never, in any real
  browser) is now translated too, for consistency rather than necessity.
- Deliberately not translated: the two-character `Auto`/`×1`/`×2` cleaning-pass
  chip labels and the `CHIP_TO_OPTION`/`OPTION_TO_CHIP` values they map
  to — those values are the integration's own literal `select` entity
  option strings, sent verbatim in service calls; translating the display
  text without touching the underlying value was judged not worth the
  added indirection for three symbol-like labels.
- Bundle size: 143.0 kb → 280.6 kb. The 8 complete dictionaries are baked
  directly into the single distributed JS file, consistent with this
  project's existing single-bundle distribution model rather than
  lazy-loaded per-locale chunks.

**Not picked up this cycle** (carried forward, still open): Map-tab framing
verification, EPHEMERAL zone/door/furniture overlays, Why?/Route/Map on
ronluna's S9+ and boutXIII's Braava m6 — all pure field-observation items,
no card code blocked on them. Full backup/restore actions and
`relocalisation_rate.percentile_rank` — considered, deliberately not scoped.

## Contract guard *(new, development)*

`tests/slugs.test.ts` checks every status value the card compares against
(`src/slugs.ts`) against the state keys in the integration's
`translations/en.json` (checked-in extract
`tests/fixtures/integration-states.json`; refresh with
`python3 scripts/update_contract.py <path-to-ha_roomba_plus>`). It also scans
`src/` for comparisons against retired display strings. A value the
integration renames now turns the build red instead of turning a feature
silently off — the failure class behind #17.

## Integration-side gaps found by this release — fixed in 4.2.19 / 4.3.0b7

- **Renamed rooms:** a room renamed in the integration's options appeared
  under its new name in the room picker, but `clean_room` knew only the
  original name ("Unknown room(s)"). Both names work now.
- **Prime-only installs** had no history endpoints, and the rooms-overdue /
  room-history sensors were never created. Both fixed; the card picks up the
  Prime rooms-overdue sensor.
- **Hazards endpoint** returned obstacle and keep-out centroids in map units
  next to stuck hotspots in robot coordinates. Each pin now carries `space`;
  the card uses it (see the Map tab section).
