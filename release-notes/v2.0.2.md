# v2.0.2 — EPHEMERAL Targeted-Clean Fix + Three-Tier Mission Result

Two fixes, both found via continued screenshot/data review of a live
Roomba 980 (EPHEMERAL tier).

---

## Bug fix: room targeting offered for EPHEMERAL robots, then failed on tap

Confirmed against integration source: `roomba_plus.clean_room` throws a
`ServiceValidationError` for any robot where `map_capability != SMART`:

> "{entity_id} does not support Smart Map room cleaning. Only i7, s9, and
> j-series robots support this action."

The card's multi-select room picker (header "Rooms…" button, the resulting
chip list, and the "Start N selected rooms" action) is built entirely around
that service call. It was gated on `caps.hasZones`, which is `true` whenever
**either** `select.*_smart_zone_select` (SMART) **or** `select.*_zone_select`
(EPHEMERAL) exists. EPHEMERAL robots like the 980 do have real, confirmed
zones in `zone_select` — so the picker rendered fully, with real room names,
promising a targeted clean that would then throw on tap.

EPHEMERAL's actual zone-cleaning model is entirely different — confirmed in
`select.py`'s `ZoneSelect` docstring: *"Selecting a zone does not immediately
start cleaning — the user presses the ZoneCleanButton to trigger the actual
mission."* Single-zone selection plus a separate button, no multi-select, no
ordering, no `clean_room` call. The card doesn't implement this model at all.

**Fix:** the multi-select picker — header button, the chip list it opens,
the Map tab's room-overlay tap-to-select, and the card-size estimate — now
gates strictly on `caps.hasSmartZones` instead of `caps.hasZones`. EPHEMERAL
robots simply don't see a room-targeting entry point until the actual
`ZoneSelect` + `ZoneCleanButton` workflow is built as its own widget — a
larger future feature, not attempted here, since it's a genuinely different
interaction model rather than a gating tweak.

(The Map tab's room polygon overlay was already correctly SMART-only, since
it depends on `hasAlignment` — confirmed in v2.0.1 that EPHEMERAL robots
never get UMF alignment data at all. Only the header button, the chip-list
fallback, and the card-size estimate needed the fix.)

## Mission result: three tiers instead of two

User feedback, and it's correct: *"stuck_and_resumed ist aus cloud sicht
completed, battery error kann auch aus cloud sicht completed sein — in
beiden fällen wurde die mission beendet."* The v2.0.1 fix already grouped
`stuck_and_resumed` with `completed` as a success — but everything else
still mapped to a single ✗ failure icon, conflating "did the mission end"
with "was it a clean success." A mission that ended with `error_battery`
isn't the same situation as a robot still stuck and unrecovered.

Three tiers now, based on `REST_API_CONTRACT.md`'s `result` enumeration:

| Icon | Tier | `result` values |
|---|---|---|
| ✓ | success | `completed`, `stuck_and_resumed` |
| ⚠ | caution — mission ended, with an incident | `cancelled`, `cancelled_by_user`, `error` and any `error_*` value (e.g. `error_battery`), `unknown` |
| ✗ | failure — never recovered, or never ran | `stuck`, `stuck_and_abandoned`, `blocked_timeout` |

`unknown` defaults to caution rather than failure — an unclassified result
doesn't confirm anything went wrong, so treating it as a hard failure would
overstate the severity.

This is purely a card-side classification; the underlying `result` value
itself, and which mission detail rows it appears in, are unchanged.
