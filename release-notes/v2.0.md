# v2.0.0 — Header + Tab Architecture Redesign

A complete rebuild of the card's layout. The six-zone stacked design from
v1.x — Status, Rooms, Health, Schedule, Alerts, History all permanently
visible, always at full weight — is replaced by a persistent header plus
four tabs (**Map**, **History**, **Health**, **⚙**). This is the trigger for
the major version bump, not any single feature.

**Requires:** `roomba_plus` ≥ 2.8.6 · Home Assistant ≥ 2024.1

v1.7.0 and v1.8.0, originally planned as incremental steps toward this, were
cancelled — their scope is absorbed into this release.

---

## Why the redesign

The v1.x layout showed every zone at maximum weight regardless of whether it
was relevant in the moment. A user checking "did the robot run today?" had to
scroll past consumable bars, schedule data, and alert text before reaching
anything spatial. Health data that's relevant once a month occupied permanent
vertical space every time the card rendered.

The new layout separates content by how often it's actually checked: status
(always, via the header), spatial history (daily — Map/History tabs),
maintenance (monthly — Health tab), and configuration (occasionally — ⚙ tab).

---

## Persistent header

Replaces the old Status zone. Shows live state and at most two action
buttons — three only while Paused — instead of a static row of every
possible action:

```
● Cleaning · Kitchen · 67%
████████████░░░░░░░░
[ ⏸ Pause ]   [ 🏠 Return home ]
```

The mission-destination line and the mission-progress line, which the
original incremental plan would have rendered as two separate lines, are
merged into one. When `sensor.*_mission_progress` is available it drives the
line (current room + percentage); otherwise the header falls back to the
older `mission_destination`-only display.

Tapping **Rooms…** expands a chip-based room picker beneath the header. Any
selection there — or a room tapped directly on the Map tab overlay (see
below) — swaps the header's action button to **Start N selected rooms**, both
pickers share the same underlying selection.

---

## Map tab

Promotes the v1.5 coverage heatmap + hazard pins to a first-class tab for
SMART and EPHEMERAL robots (anything with `image.*_coverage_map`), available
in standalone mode. Companion mode hides this tab entirely, since
xiaomi-vacuum-map-card already owns the spatial view when present.

**Room boundary overlay (SMART, calibrated only):** room polygons drawn over
the heatmap from the `rooms` attribute, with tap-to-select. Source-verified:
these coordinates are pose-space millimetres, not image pixels — the same
mm→% transform already used for hazard pins is reused here rather than a new
one being built.

**EPHEMERAL robots** (e.g. the 980) get the heatmap and hazard pins without
named room boundaries — no UMF alignment exists for this tier — but the
integration's `OutlineStore` automatically bakes a self-sharpening floor
outline into the image after a few missions, with no card-side work required.

## History tab

The v1.x calendar heatmap, day detail, and lifetime stats, now with a
merged day-detail row: the room sequence (F12) and per-room coverage (F8),
previously two separate lines, are now one —

```
🍳 Kitchen 75% → 🚪 Hallway 60% → 🛁 Bathroom 58% → 🛏 Bedroom
```

— sourced from `last_cleaned_rooms` (already ordered) and `room_coverage`
zipped together; no third "traversal sequence" attribute exists, despite an
earlier plan draft assuming one did.

The calendar heatmap's SVG now scales responsively (`clamp(88px, 100%,
200px)` via CSS) for its new full-width tab context, instead of rendering at
a fixed 200px regardless of available space. The coordinate geometry inside
the SVG itself is unchanged — this is a presentational change only, so none
of the existing fixed-geometry heatmap tests needed to change.

In `mode: companion`, this tab gains the Calendar/Coverage sub-tab toggle
(since there's no separate Map tab to hold the coverage view in that mode).

## Health tab

**Robot health score** — `sensor.*_robot_health_score` (note: the correct
entity key, corrected from an earlier plan draft that referenced
`robot_health`). Shown prominently with a colour band; the individual
filter/brush/battery/tank bars collapse underneath by default — tap **Show
details** to expand. A "Calibrating…" placeholder appears while the
integration hasn't yet accumulated 20 missions / 3 of 5 input signals,
rather than showing a misleading zero.

This score is unrelated to `sensor.*_integration_health` (a separate
integration-diagnostic sensor with its own band system) — the two must never
be confused.

**Maintenance calendar** — wheel/contact/bin "last cleaned" rows below the
consumable bars, with "Never recorded" shown for sensors that exist but have
never had a reset service called.

**Mission anomaly banner** — built and tested, but currently inactive: the
integration doesn't yet expose `consecutive_anomalous` on
`last_mission_result`. The code activates automatically once a future
integration release adds it.

**Tab badge** — lights up on a low health score, an overdue maintenance
sensor, or any alert tagged `category: 'health'` (see Alerts below).

## ⚙ tab

Schedule + presence intelligence, the settings panel (edge clean / always
finish / carpet boost), room targeting for standalone mode, and maintenance
service-call references for Developer Tools.

**Bug fix incidental to this consolidation:** the settings panel was
previously only reachable through the room selector zone, which returns
empty before reaching the settings panel when the robot has no zone
capability (`hasZones: false`) — silently hiding carpet boost / edge clean /
always finish entirely on 600-series robots. The ⚙ tab now renders the
settings panel independently, so it's no longer coupled to room-targeting
capability.

**Bug fix:** the carpet boost select entity was referenced internally as
`select.*_carpet_boost_mode`; the correct entity is
`select.*_carpet_boost_select`. This was a card-internal lookup bug, not a
config option — no user action needed.

## Alerts → tab badges

The old Alerts zone (a single always-visible banner showing the
highest-priority active issue) is partially superseded by tab badges. Each
alert condition is now tagged with a category:

| Alert | Category |
|---|---|
| WiFi signal dead-zone during last mission | **History** |
| Maintenance due, filter/brush wear rate, navigation quality, consecutive skipped cleans | **Health** |
| Live error | *(none — already shown continuously in the header)* |

The single-banner display still exists (now inside the Health tab) and still
shows only the highest-priority alert at a time, but badges reflect every
active category independently — a WiFi problem stays flagged on the History
tab's badge even while a higher-priority error is occupying the Health tab's
banner text.

Both the banner and the badges read from one shared function
(`collectAlerts()` in `alert-zone.ts`) so the underlying thresholds — wear
ratio > 1.5×, navigation quality < 60, etc. — can't drift out of sync between
the two surfaces.

**Not yet implemented:** a literal one-badge-per-alert-type breakdown within
a tab (e.g. distinguishing a wear alert from a navigation alert on the same
badge). Currently each tab gets a single binary badge regardless of how many
of its category's conditions are active.

## SC1 sensor migration

Three sensors deprecated by the integration (v2.7.0, removed in v3.0) are
migrated to their replacements:

| Old (deprecated) | New |
|---|---|
| `sensor.*_recent_wifi_floor` | `sensor.*_wifi_health` — **not a like-for-like swap**, see below |
| `sensor.*_cleaning_speed_trend` | `sensor.*_cleaning_performance` attr `trend` |
| `sensor.*_recent_area_30d` / `_recent_time_30d` | `sensor.*_cleaning_analytics_30d` (state + `time_h` attr) |

**WiFi floor is a genuine semantic change, not a rename.** The deprecated
sensor was independently confirmed buggy — declared as a percentage but
actually returning a raw 0–4 signal-bucket index. `wifi_health`'s state is a
real weighted-average quality percentage, a different statistic from the old
"floor" value. The card preserves the alert's original intent (was there a
dead zone during the mission) by reading the new `weakest_bucket_observed`
attribute instead of the average state.

**Bug fix found and fixed during this migration:** the old `recent_time_30d`
sensor's native unit is minutes, but the pre-v2.0 card parsed it into a
variable named `hours` and displayed it with an "h" suffix — a pre-existing
display bug. The new `cleaning_analytics_30d` sensor's `time_h` attribute is
genuinely in hours, so the lifetime stats footer's time figure is now
correct, not just renamed.

## Household view

The robot selector dropdown (2+ robots configured) gains a **📊 Household
summary** option. Selecting it replaces the header and tabs entirely with the
combined multi-robot view — previously this content was permanently appended
below every tab regardless of whether anyone wanted to see it. A **← Back**
chip returns to the per-robot view.

## Upgrade notes

**Config compatibility:** all existing `show_*` options continue to work
unchanged. `show_settings` is deprecated in favour of `mode: companion` but
still accepted as an alias.

**If you use xiaomi-vacuum-map-card:** add `mode: companion` to your config.
The previous `show_rooms: false` pattern still works but no longer hides the
Map tab (which didn't exist before v2.0) — `mode: companion` is now the
correct way to defer spatial interaction to XVMC.

**Min integration version raised to 2.8.6.** This is required for the SC1
sensor migration and the v2.0 features (robot health score, maintenance
calendar, mission progress sensor). Users on older integration versions
should update the integration before — or at the same time as — this card.

**No action needed for the bug fixes** (carpet boost entity lookup, settings
panel visibility on zone-less robots, lifetime stats time unit) — they take
effect automatically.

## Known gaps in this release

- Mission anomaly banner is built but inactive pending an integration update
  (`consecutive_anomalous` attribute not yet exposed)
- Header's "Start selected rooms" button has no loading spinner during send
  (the ⚙ tab's own room-targeting button does)
- Household view shows no loading skeleton while data is in flight
- EPHEMERAL robot zone/door overlays are not yet possible — the integration
  doesn't currently expose this data in a drawable form
- Per-alert-type badge granularity within a single tab is not implemented —
  each tab gets one binary badge, not one per alert condition
